## 0. 一句话背景

海风哥 2026-08-08 提出：给 Lumen 加一个移动端。不支持本地命令行，登录后远程控制
PC 上的 Lumen；由 PC 启动一个**不显示界面的 headless LLM CLI 子进程**，把结构化
对话内容转发到手机，手机上显示成**气泡流**（像 Claude 移动端那样），而不是终端画面。

关键形态判断：移动端是「Lumen 远程控制协议的**第三种控制端**」。它不镜像终端画面、
不参与 P2P 直连，只跑一条新增的 LLM 对话数据面。

## 4. 已拍板的决策（别再重新讨论）

蓝图 §2 有完整的 K1–K17 表。这里只列**最容易被推翻重议**的几条：

| # | 决策 | 依据（一句话） |
|---|---|---|
| K1 | 原生 Flutter App，**不做 Web/PWA** | 服务端 WS 只认 `Authorization` 头，浏览器 `WebSocket()` 设不了自定义头；且全仓无 CORS 层 |
| K2 | **不用 flutter_rust_bridge**，手写 Dart 模型 + golden 语料 CI 双向断言 | FRB 不走 serde，而本 crate 的协议语义（外部标签、`with=b64`、`transparent`、`flatten`）全寄生在 serde 属性上——桥过去的是内存结构体，**线格式一个字节都没带过去** |
| K3 | `RemoteFrame` 只加 1 个变体，子协议内部标签 + `serde(other)` 兜底 | 外部标签枚举不支持 `other`，不兼容代价只付这一次 |
| K4 | `PROTOCOL_VERSION` 4，`MIN_SUPPORTED_VERSION` **保持 3** | 隐藏会话由 **caps 握手**门控，不由版本号门控；上调 MIN 会把 v3 桌面端的终端镜像一起挡掉 |
| K5 | 老端不兼容靠 `LlmHello` 5s 超时 + `Notice::LlmPeerTooOld` + UI 提示 | 仓库注释里那个 `MIN_SUPPORTED_VERSION` 版本门**是愿望、没有代码**，且两端在协议层根本看不到对端版本 |
| K9 | P0 权限 = `acceptEdits` + `--add-dir` 围栏；`bypassPermissions` 桌面也不提供 | 本版 CLI 无 `--permission-prompt-tool` |
| K10 | 图片附件复用现成的 `PutBegin/PutChunk/PutEnd` 通道，`Send` 只带路径 | REST 无上传端点 + 1 MiB body 上限；文件终点本来就在 PC |
| K11 | `mobile/` 在仓库顶层，**内部不放任何 Cargo.toml** | 根 `[workspace]` 既无 `exclude` 也无 `default-members`，放进去会被误当成员 |
| K14 | 桌面端**只做图标标识**，不做会话 UI | 海风哥拍板 |

**2026-08-09 三条拍板**：
1. **被控端锁屏不阻断工具调用**（锁屏只锁桌面本地交互）。
2. **桌面镜像开着时手机可同时接入**——因为手机端是「隐藏会话」，不是 Tab/Session、
   桌面端不显示、只给一个图标标识。这条要求改服务端仲裁，已在片 4b 落地。
3. **桌面端不做会话 UI**。

## 5. ★ 踩过的坑（最有价值的部分，逐条读）

### 5.1 环境坑

| 坑 | 现象 | 对策 |
|---|---|---|
| **本机常驻 http 代理** | `flutter test` 卡死；`pub` 拉不动 | `env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY`；pub 走 `PUB_HOSTED_URL=https://pub.flutter-io.cn`。**已封进 `mobile/tool/test.ps1` 与 `test.sh`，直接用脚本** |
| **PowerShell 的 `>` 重定向毁 UTF-8** | 采样 `claude` 输出时，中文按 GBK 解码再重编码，JSON 结构被打散且**不可逆**（13 行坏 2 行） | 采样用 `cmd /c "... > f.jsonl"` 或 Git Bash；或先 `[Console]::OutputEncoding = [Text.Encoding]::UTF8` |
| **Claude Code 内起嵌套 `claude` 子进程必 403** | `apiKeySource: "none"`，模型调用被拒 | 这是刻意限制，**不要绕**。要采样必须在普通终端跑 |
| **`pub` 会把镜像 URL 写回 `pubspec.lock`** | CI 跑 `--enforce-lockfile` 时因 URL 是国内镜像而失败 | lock 已归一到 `pub.dev`；脚本只在解析阶段用镜像、写回前恢复，并有断言防回归（`mobile/test/pubspec_lock_test.dart`） |

### 5.2 Windows 平台坑

**`std::process::Command` 不查 `PATHEXT`**（本轮最贵的一条）。它只给无扩展名的程序名
追加 `.exe`。而 `claude` 是 npm 装的，`%APPDATA%\npm` 下只有 `claude` / `claude.cmd` /
`claude.ps1`，**没有 `claude.exe`** ⇒ `Command::new("claude")` 必然 `NotFound`，
**整条链路起不来**。

这条最要命的地方是：片 2 的全部单测都绿，因为**没有一条真的 spawn 过进程**。
修法在 `llm_runner/proc.rs` 的 `resolve_program()`：自己按 `PATH` × `PATHEXT` 解析，
并与 `LAUNCHABLE_EXTS`(`.exe/.com/.bat/.cmd`) **取交集**——`PATHEXT` 默认还含
`.VBS/.JS/.MSC`，那些 `CreateProcessW` 起不来（`ERROR_BAD_EXE_FORMAT`），
**认了却起不来比不认更糟**。

### 5.3 协议与兼容性坑

**两种降级形态的危险度差一个量级——这是片 4b 全部设计的支点：**

- 未知**变体**在外部标签枚举下 ⇒ 整条解析失败 ⇒ **可控**（状态零污染，配超时即可变成一句人话）
- 未知**字段**⇒ 静默忽略后**按老语义执行成功** ⇒ **不可控**
  （新手机发 `RequestControl{kind:"Llm"}` 给老服务端，会真的建一条镜像会话，
  凭空占住那台 PC 的独占位，两端都察觉不到）

所以控制面**一律新增变体，绝不给已有变体加语义字段**。

**`DenyReason` 零新增变体**，与数据面口径相反且必须相反：它随 `ControlDenied` 下行，
加变体会让老客户端整条解析失败，丢掉的正是它**唯一的拒绝回执** ⇒ UI 永久转圈。
数据面加 `RemoteFrame` 变体有 5 秒握手超时兜底，控制面加拒因**没有任何兜底**。

**「服务端零改动」不成立**（原始判断被对抗验证推翻）。数据面盲转确实零改，但：
- 前提是**原生 App**（WS 只认 `Authorization` 头 + 全仓无 CORS）
- 移动链路会踩服务端四处既有空白：无背压、超 4 MiB 是**断连不是丢帧**、
  无 idle 超时/不发 WS Ping、45 秒在线窗口
- 「手机与桌面镜像并存」要改**控制面**仲裁，服务端会反序列化 ⇒ 破坏性变更

**同版发布要求**：服务端↔被控端 PC、服务端↔手机端**必须同版**；
服务端↔桌面控制端**不需要**（线格式一字节没变）。
老服务端遇到新变体是「解析失败后继续读、完全无回音」⇒
**手机端必须自带 `OpenHidden` 发起超时（12 秒）判定「服务器版本过低」**，
否则就是无限转圈。**这是片 5/6 的硬验收项。**

### 5.4 ★ 白名单转发铁律（安全，不可协商）

实测发现 `system.subtype = "hook_started"` / `"hook_response"` 也会出现在 stdout
事件流上，而本机那条 `hook_response` 的 `stdout` 字段**携带了 4106 字符的
engram 私人记忆库全文**。若 PC 侧把事件原样中继给手机，用户配置的任意 hook 输出
（可能含密钥、内网信息）会经中继服务器传到手机。

**结论：PC → 手机必须白名单转发，绝不能黑名单过滤或原样透传。**
协议类型设计上不留 `Raw(serde_json::Value)` 这种直通口子。

**这条的证据是四次连续的翻车**：脱敏样本时，第一次点名了 `output` 却漏了同一行的
`stdout`；第二次 `filePath` 换了、`input.file_path` 漏了；第三次子代理又漏一处；
第四次 `init` 行的 `plugins`/`skills`/`cwd` 全露着（而 lumen 是公开仓库）。
**每一次都是"点名字段"的做法输给了白名单。** 最终改成白名单：`init` 行只保留
14 个通用键的原值，其余键的值一律中和成计数占位符。

### 5.6 实现层面抓到过的 blocker（同类错误别再犯）

- **只测单包漏掉跨 crate 编译面**：片 0 只跑 `cargo test -p lumen-protocol`，
  漏掉 `remote_ws.rs` 里对 `RemoteFrame` 的**穷尽 match**，整个 workspace 编译不过。
  ⇒ **收尾必须跑 `cargo check --workspace`**。
- **装饰常量**：曾新增一个上限常量并声称"堵住了一条真缝"，实测**全仓零代码引用**，
  反序列化里没有任何长度校验。⇒ 新增上限常量必须有真实引用点与测试。
- **帧体积翻倍**：`RemoteFrame` 从 144 B 涨到 312 B（内联了 `LlmFrame`），
  **clippy 不报**。改 `Box` 压回 144 B，并加测试断言
  `size_of::<RemoteFrame>() < size_of::<LlmFrame>()` 守住。
- **`Delta` 单帧无上限**能顶穿服务端 4 MiB 把整条 WS 打断（终端镜像一起断）。
  连带：`ack_map` 的 `(0, tseq)` 占位机制在一池发 N 帧后前提失效，
  **ACK 走完反而一条 transcript 都销不掉**。
- **`attach()` 用 `known_seq > seq` 判重同步**：水位相等但内容已丢时静默判"已同步"。
  丢弃点（`reset_protocol_state` / `detach`）会把没领 seq 的 pending 整个丢掉而
  **`seq` 一动不动**，光比水位永远发现不了。

## 7. 工作方法（这套流程抓到了上面所有的坑，建议延续）

每一片都走同一个模式：**实现 → 对抗验证 → 修复**，并且：

1. **验证代理必须亲自跑命令，不许信实现代理的转述。** 前面每一轮都靠这条抓到东西：
   "整个 workspace 编译不过"、"整条链路在本机起不来"、"常量零引用"、"lock 里全是镜像 URL"。
2. **验证的任务是证伪，不是复查。** prompt 里明写「默认怀疑」「宁可报 minor 也不放过」
   「找到一条泄漏路径就是 blocker」。
3. **收尾命令固定**：`cargo check --workspace` + `cargo clippy --workspace --all-targets -- -D warnings`（CI 口径）+ 各包 test。
4. **cargo 很贵**（`lumen-app` 是超大 crate），中间步骤别反复跑，写完一整块再跑，
   全程控制在 5 次以内。
5. **不要在 `lumen-protocol` 上跑 `cargo fmt`**——该仓库 HEAD 本身不是 rustfmt-clean，
   会重排大量无关既有代码。要格式化只对新建单文件跑 `rustfmt --edition 2021 <file>`。
6. **代码质量判据**（海风哥要求按《代码大全》）：函数 ≤ 200 行（目标 ≤ 60）、
   圈复杂度 ≤ 10、参数 ≤ 7、嵌套 ≤ 4 层；每个新模块要能回答「它隐藏了什么设计决策」
   （答不上来 = 假拆分）；内聚低于「通信内聚」的方案作废。
   **目前 M7 新代码全部达标**：`llm_runner` 264 函数中位 6 行最长 103；
   `remote_ws/llm.rs` 76 函数中位 13 最长 78；`hub.rs` 32 函数中位 8 最长 71；
   超 200 行的 **0 个**。

## 9. ★ 两个 HUD bug（海风哥 2026-08-09 报，**同日已修**）

> 这两条是 LLM HUD 的 bug，**与 M7 无关**（M7 是移动端远程控制，HUD 是桌面端既有功能）。
> 改动集中在 `llm_cli.rs`（刮取与分类）与 `shell/hud.rs`（额度数据源），
> 没有动 `shell/hud.rs` 的 Used/Remaining 换算——那一侧本来就是对的。

### 取证得到的地面真相（先看这个，两个 bug 都由它解释）

海风哥的 `~/.claude/settings.json` 配了自定义状态行：

```json
"statusLine": { "type": "command", "command": "bash \"C:/Users/jimhy/.engram/engram-statusline.sh\"" }
```

该脚本内部调 **claude-hud 0.3.0**（语言 `zh-Hans`）再拼上 engram 段。
所以 Lumen 从屏幕底部刮到的**根本不是 Claude Code 自带的状态行**。
实跑该脚本、剥掉 ANSI 后逐字得到（**一整行**）：

```
上下文 ░░░░░░░░░░ 1% │ 用量 █████░░░░░ 45% | 本周 ███░░░░░░░ 30% (重置剩余 6d 19h)   ● Engram | L1:1 L2:1 L3:13
```

复现命令（可重跑）：把一份 statusline JSON 喂给脚本即可，
JSON 字段形状见 Claude Code 二进制里的 statusline 契约（`context_window` /
`rate_limits.{five_hour,seven_day}` / `cost` / `model` / `workspace`）。

顺带取到 Claude Code **2.1.226 自带**状态行的三种形态（从 `bin/claude.exe` grep 出的源码，
274 MB 单文件把 JS 全打包进去了，只能 `grep -a -o` 加窗口捞）：

```js
let rdv = tdv ? `${100-OKm}% context used` : `${OKm}% until auto-compact`;   // OKm = 剩余百分比
// 低水位分支：`Context low (${pct}% remaining)[ · /model opus[1m] | · Run /compact to compact & continue]`
```

注意 `% until auto-compact` **不含 `context` 字样**，老代码会把它整条忽略。

### Bug 1：HUD 上下文语义被反转 —— 根因是**整行**关键词匹配跨段误命中

`hud_context_from_line` 原来拿**整行**做子串匹配：`上下文` 命中 ⇒ 认这一行；
`percent_in_line` 取行内第一个百分比 ⇒ `1%`（**数字其实是对的**）；
然后关键词表里的 `剩余` 被 **「重置剩余」** 命中 ⇒ 判成 `Remaining`。
于是「已用 1%」显示成「剩余 1%」，进度条一并反成 99%。

**这是 zh-Hans 专属 bug**：英文语言包那半边是 `resets in`，不含任何关键词，判定正确。

**修法**：判定单位从「整行」降到「分段」。状态行用 `│ ┃ | · •` 分隔多组指标
（`hud_model` 早就在按这套分段，现在提取成 `SEGMENT_SEPARATORS` 共用），
只在**含上下文字样的那一段**内取百分比与判语义。同时：

- 一段里「已用」与「剩余」两种措辞**同时**出现 ⇒ 返回 `None`（宁可空着，不显示反的数）；
- `until auto-compact` 加进「剩余」措辞表，并放宽入口条件收下这种不带 `context` 的写法；
- `percent_in_line` 遇到越界值（`999%`）原来会 `?` 掉整段扫描，改成只跳过它自己。

**没有改成「两者都不匹配就不显示」**：带进度条的裸百分比（`Context ██░░ 45%`、
`上下文 ░░ 1%`）是各家 CLI 的通用画法且一律指已用，要求必须出现「已用」字样
会把最常见的形态整个变成不显示。歧义保险改放在「两种措辞同时出现」这一处。

### Bug 2：Claude 的 HUD 缺「5 小时/本周用量」—— 补了状态行刮取通路

同一行里 `用量 45%`（5 小时）与 `本周 30%`（周）**早就画在屏幕上**了，只是没人解析。
新增 `hud_usage_from_line`，按同一套分段规则取窗口标签、百分比与
`(重置剩余 6d 19h)` 形式的倒计时，产出 `HudUsageWindow{label:"5h"|"7d", used_percent, resets_in}`，
经 `HudView.usage` 送到 `usage_section`。

**数据源优先级与上下文相反**：额度是 **JSON 优先、画面兜底**。
Codex/Kimi 有结构化 JSON 原值（`llm_hud.rs` 的 `codex_usage_windows`），
不能让一次画面误匹配盖掉准确数据；Claude 没有 JSON 通路，才吃画面这条。
并且**画面刮取本身就只对 Claude 开**（`hud_usage` 头一行按 `kind` 拦掉其余 CLI）——
两道门是有意重复的：优先级只决定谁赢，`kind` 那道门让别的 CLI 根本不产生候选。
`usage_section` 因此从 `if let Some(details)` 块里提了出来——Claude 侧 `details` 常为
`None`，留在里面就永远不画。

**为什么不走本地文件**（取证结论，别再试）：`~/.claude.json` 的 `cachedUsageUtilization`
形状与 `UsageWindow` 几乎零阻抗（`five_hour`/`seven_day` + RFC3339 `resets_at`），
**但它是死数据**——只有 `/usage` 面板会刷新它，实测本机 `fetchedAtMs` 停在 9 天前、
期间 CLI 反复重写该文件也纹丝不动，CLI 自己超过 1 小时就不信这份缓存。
`.claude/` 目录下（`projects/` `sessions/` `stats-cache.json` `telemetry/`）**完全没有**额度信息。
真正的活数据只在 HTTP 响应头（`anthropic-ratelimit-unified-5h-*`，永不落盘）和
statusline hook 的 stdin JSON 里——后者正是 claude-hud 画到屏幕上的那份。

**有意没做的两条**（取证时看到了，判断不划算）：
1. Claude Code 接近限额时会自己打一条告警，逐字形如
   `You've used 92% of your session limit · resets 3pm`（`session limit` = 5 小时窗口，
   `weekly limit` = 周窗口）。它是**一次性滚屏消息**，会随对话滚走，
   接进 HUD 会变成时有时无的闪烁数字。
2. `/usage` 命令的对话框（`Current session` / `Current week (all models)` + 50 格进度条）
   是**临时浮层**，要用户手敲命令才出现，同样不是常驻数据。

**已知局限（有意接受）**：这条通路要求用户的状态行确实显示了额度。
没装 claude-hud（或类似状态行）时 Claude 的额度区不显示——这是诚实的空，不是错的数。
另：claude-hud 若把 `contextValue`/`usageValue` 配成 `remaining`，画出来是裸的剩余百分比、
**屏幕上没有任何可区分的措辞**，此时会被读成已用。这个洞从画面上无法弥合。

### ★ 对抗验证在「已经全绿」的新代码里又抓出三条

**这三条全都活在 30 条测试全绿的状态下**，原因是测试语料挑的都是恰好绕开陷阱的变体。
逐条记下来，因为它们是同一类错误的三种长相：

1. **标签与数字配错（静默出错值）**。Claude Code 官方文档自带的状态行例子是
   `5h:45% 7d:30%`——同一段里并排两个窗口、中间没有任何分隔符。
   按「整段取第一个百分比」会产出 `[7d = 45%]`。修法：分段之后再按窗口名的
   出现位置切一刀，每个窗口名到下一个窗口名之间才是它自己的数。
2. **倒计时被吞掉（静默丢数据）**。`reset_countdown` 原来用 `rfind('(')` 只看最后一个括号。
   engram 状态行**空闲态**（会话刚开、状态文件还没生成时的常态）在行尾拼
   `● Engram (idle)`，而且是三个空格拼接、**不带分隔符**，所以它落在周窗口那一段里
   ⇒ 真倒计时被 `(idle)` 顶掉。修法：逐个括号从左往右试，取第一个能解析出时长的。
3. **`15h` 里的 `5h` 被当成窗口名（前两条修完后新引入的）**。加了按位置切片之后，
   倒计时 `4d 15h` 中的子串 `5h` 会命中 5 小时窗口的名字，把周窗口的切片从括号中间截断。
   修法：窗口名前面不能紧挨着字母数字（`starts_at_word_boundary`）。

顺带堵掉一条同类的：`percent_in_line` 只吞连续整数位，`77.5%` 会读成 **5**。
现有来源都是整数所以没暴露，但 `/context` 面板那张表逐字就是 `.toFixed(1)`。改成连小数一起吞。

### 残留风险（**已知未修，下一个人接手前先读**）

| 风险 | 为什么不修 |
|---|---|
| 措辞表之外的说法会被默认判成「已用」且无告警（例如「上下文余量 63%」，「余量」不在表里） | 这是 Bug 1 的同构下一个坑，只是换了个词。不靠猜着往表里加词——加没实证过的措辞正是本项目一贯不做的事。要根治只能等到能拿到结构化原值 |
| `view.context.or_else(...)`：画面刮取只要返回 `Some` 就永不回退到 JSON。屏幕上任何一行含 `context` + `NN%` 的文字（cat 一份日志、甚至对话正文本身）都能霸占 Codex/Kimi 的 HUD 并盖掉准确的 JSON 值 | **是既有行为，不是本次引入**。改它会动到 Codex/Kimi 的既有表现，超出这次的范围。额度那一侧我已经反过来做（JSON 优先），上下文这侧要不要跟着翻需要单独拍板 |
| `hud_metrics` 自下而上取行，赌「状态行永远在最底部」。CLI 进了全屏面板（`/context`、`/usage` 的浮层）时这个假设不成立 | 既有行为；浮层是临时的，关掉即恢复 |
| claude-hud 的上下文百分比**是它自己按 token 数算的**，不是直接用状态行 JSON 里的 `used_percentage`（实测喂 0 它画 1%） | 意味着 HUD 上那个数是插件的口径。将来若同时接入 JSON 通路与画面通路，两者会对不上，得先定以谁为准 |
| 两套 `utilization` 标度：HTTP 响应头派生的是 0–1 小数，`/usage` API 与 `.claude.json` 里的是 0–100 | 现在只有一条通路所以不会撞。哪天接第二条，先统一标度再接，否则就是「45% 显示成 0%」这种静默错 |

**将来若画面这条路断了**，唯一干净的备胎是 `control_request` 的 **`get_usage`**
（其自述逐字：*Requests the structured /usage data: session cost/usage totals plus
claude.ai plan rate-limit utilization when available. Experimental — the response shape may change.*）。
`llm_runner/claude.rs` 的 `encode_control_request` 已经通了三个 subtype，加一个边际成本很低。
但它要另起 headless 进程 + 走网络 + 协议自称 experimental，**且算不算违反「不注入命令」需要海风哥拍板**，别当首选。

**绝对不要做的一件事**：让 Lumen 去写用户的 `settings.json` 装自己的状态行。
`statusLine` 是**单槽位**，本机已被 engram（内含 claude-hud）占用，写进去会把用户现有状态行整个顶掉。
正确姿势是刮别人已经画好的，不是装自己的。
