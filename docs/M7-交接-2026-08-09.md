## 0. 一句话背景

海风哥 2026-08-08 提出：给 Lumen 加一个移动端。不支持本地命令行，登录后远程控制
PC 上的 Lumen；由 PC 启动一个**不显示界面的 headless LLM CLI 子进程**，把结构化
对话内容转发到手机，手机上显示成**气泡流**（像 Claude 移动端那样），而不是终端画面。

关键形态判断：移动端是「Lumen 远程控制协议的**第三种控制端**」。它不镜像终端画面、
不参与 P2P 直连，只跑一条新增的 LLM 对话数据面。

## 4. 已拍板的决策（别再重新讨论）

蓝图 §2 有完整的 K1–K17 表。这里只列**最容易被推翻重议**的几条：

| # | 决策 | 依据（一句话） |
|---|---|---|
| K1 | 原生 Flutter App，**不做 Web/PWA** | 服务端 WS 只认 `Authorization` 头，浏览器 `WebSocket()` 设不了自定义头；且全仓无 CORS 层 |

| K9 | P0 权限 = `acceptEdits` + `--add-dir` 围栏；`bypassPermissions` 桌面也不提供 | 本版 CLI 无 `--permission-prompt-tool` |
| K10 | 图片附件复用现成的 `PutBegin/PutChunk/PutEnd` 通道，`Send` 只带路径 | REST 无上传端点 + 1 MiB body 上限；文件终点本来就在 PC |
| K11 | `mobile/` 在仓库顶层，**内部不放任何 Cargo.toml** | 根 `[workspace]` 既无 `exclude` 也无 `default-members`，放进去会被误当成员 |

## 5. ★ 踩过的坑（最有价值的部分，逐条读）

### 5.1 环境坑

| 坑 | 现象 | 对策 |
|---|---|---|
| **本机常驻 http 代理** | `flutter test` 卡死；`pub` 拉不动 | `env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY`；pub 走 `PUB_HOSTED_URL=https://pub.flutter-io.cn`。**已封进 `mobile/tool/test.ps1` 与 `test.sh`，直接用脚本** |
| **PowerShell 的 `>` 重定向毁 UTF-8** | 采样 `claude` 输出时，中文按 GBK 解码再重编码，JSON 结构被打散且**不可逆**（13 行坏 2 行） | 采样用 `cmd /c "... > f.jsonl"` 或 Git Bash；或先 `[Console]::OutputEncoding = [Text.Encoding]::UTF8` |
| **Claude Code 内起嵌套 `claude` 子进程必 403** | `apiKeySource: "none"`，模型调用被拒 | 这是刻意限制，**不要绕**。要采样必须在普通终端跑 |
| **`pub` 会把镜像 URL 写回 `pubspec.lock`** | CI 跑 `--enforce-lockfile` 时因 URL 是国内镜像而失败 | lock 已归一到 `pub.dev`；脚本只在解析阶段用镜像、写回前恢复，并有断言防回归（`mobile/test/pubspec_lock_test.dart`） |

### 5.2 Windows 平台坑

**`std::process::Command` 不查 `PATHEXT`**（本轮最贵的一条）。它只给无扩展名的程序名
追加 `.exe`。而 `claude` 是 npm 装的，`%APPDATA%\npm` 下只有 `claude` / `claude.cmd` /
`claude.ps1`，**没有 `claude.exe`** ⇒ `Command::new("claude")` 必然 `NotFound`，
**整条链路起不来**。

这条最要命的地方是：片 2 的全部单测都绿，因为**没有一条真的 spawn 过进程**。
修法在 `llm_runner/proc.rs` 的 `resolve_program()`：自己按 `PATH` × `PATHEXT` 解析，
并与 `LAUNCHABLE_EXTS`(`.exe/.com/.bat/.cmd`) **取交集**——`PATHEXT` 默认还含
`.VBS/.JS/.MSC`，那些 `CreateProcessW` 起不来（`ERROR_BAD_EXE_FORMAT`），
**认了却起不来比不认更糟**。

### 5.3 协议与兼容性坑

**两种降级形态的危险度差一个量级——这是片 4b 全部设计的支点：**

- 未知**变体**在外部标签枚举下 ⇒ 整条解析失败 ⇒ **可控**（状态零污染，配超时即可变成一句人话）
- 未知**字段**⇒ 静默忽略后**按老语义执行成功** ⇒ **不可控**
  （新手机发 `RequestControl{kind:"Llm"}` 给老服务端，会真的建一条镜像会话，
  凭空占住那台 PC 的独占位，两端都察觉不到）

所以控制面**一律新增变体，绝不给已有变体加语义字段**。

**`DenyReason` 零新增变体**，与数据面口径相反且必须相反：它随 `ControlDenied` 下行，
加变体会让老客户端整条解析失败，丢掉的正是它**唯一的拒绝回执** ⇒ UI 永久转圈。
数据面加 `RemoteFrame` 变体有 5 秒握手超时兜底，控制面加拒因**没有任何兜底**。

**「服务端零改动」不成立**（原始判断被对抗验证推翻）。数据面盲转确实零改，但：
- 前提是**原生 App**（WS 只认 `Authorization` 头 + 全仓无 CORS）
- 移动链路会踩服务端四处既有空白：无背压、超 4 MiB 是**断连不是丢帧**、
  无 idle 超时/不发 WS Ping、45 秒在线窗口
- 「手机与桌面镜像并存」要改**控制面**仲裁，服务端会反序列化 ⇒ 破坏性变更

**同版发布要求**：服务端↔被控端 PC、服务端↔手机端**必须同版**；
服务端↔桌面控制端**不需要**（线格式一字节没变）。
老服务端遇到新变体是「解析失败后继续读、完全无回音」⇒
**手机端必须自带 `OpenHidden` 发起超时（12 秒）判定「服务器版本过低」**，
否则就是无限转圈。**这是片 5/6 的硬验收项。**

### 5.4 ★ 白名单转发铁律（安全，不可协商）

实测发现 `system.subtype = "hook_started"` / `"hook_response"` 也会出现在 stdout
事件流上，而本机那条 `hook_response` 的 `stdout` 字段**携带了 4106 字符的
engram 私人记忆库全文**。若 PC 侧把事件原样中继给手机，用户配置的任意 hook 输出
（可能含密钥、内网信息）会经中继服务器传到手机。

**结论：PC → 手机必须白名单转发，绝不能黑名单过滤或原样透传。**
协议类型设计上不留 `Raw(serde_json::Value)` 这种直通口子。

**这条的证据是四次连续的翻车**：脱敏样本时，第一次点名了 `output` 却漏了同一行的
`stdout`；第二次 `filePath` 换了、`input.file_path` 漏了；第三次子代理又漏一处；
第四次 `init` 行的 `plugins`/`skills`/`cwd` 全露着（而 lumen 是公开仓库）。
**每一次都是"点名字段"的做法输给了白名单。** 最终改成白名单：`init` 行只保留
14 个通用键的原值，其余键的值一律中和成计数占位符。

### 5.5 实测确证的 Claude stream-json 事实（别再按公开 API 推定）

样本在 `docs/调研/` 与 `crates/lumen-app/src/llm_runner/fixtures/`（两处逐字节相同）。

### 5.6 实现层面抓到过的 blocker（同类错误别再犯）

- **只测单包漏掉跨 crate 编译面**：片 0 只跑 `cargo test -p lumen-protocol`，
  漏掉 `remote_ws.rs` 里对 `RemoteFrame` 的**穷尽 match**，整个 workspace 编译不过。
  ⇒ **收尾必须跑 `cargo check --workspace`**。
- **装饰常量**：曾新增一个上限常量并声称"堵住了一条真缝"，实测**全仓零代码引用**，
  反序列化里没有任何长度校验。⇒ 新增上限常量必须有真实引用点与测试。
- **帧体积翻倍**：`RemoteFrame` 从 144 B 涨到 312 B（内联了 `LlmFrame`），
  **clippy 不报**。改 `Box` 压回 144 B，并加测试断言
  `size_of::<RemoteFrame>() < size_of::<LlmFrame>()` 守住。
- **`Delta` 单帧无上限**能顶穿服务端 4 MiB 把整条 WS 打断（终端镜像一起断）。
  连带：`ack_map` 的 `(0, tseq)` 占位机制在一池发 N 帧后前提失效，
  **ACK 走完反而一条 transcript 都销不掉**。
- **`attach()` 用 `known_seq > seq` 判重同步**：水位相等但内容已丢时静默判"已同步"。
  丢弃点（`reset_protocol_state` / `detach`）会把没领 seq 的 pending 整个丢掉而
  **`seq` 一动不动**，光比水位永远发现不了。

## 7. 工作方法（这套流程抓到了上面所有的坑，建议延续）

每一片都走同一个模式：**实现 → 对抗验证 → 修复**，并且：

1. **验证代理必须亲自跑命令，不许信实现代理的转述。** 前面每一轮都靠这条抓到东西：
   "整个 workspace 编译不过"、"整条链路在本机起不来"、"常量零引用"、"lock 里全是镜像 URL"。
2. **验证的任务是证伪，不是复查。** prompt 里明写「默认怀疑」「宁可报 minor 也不放过」
   「找到一条泄漏路径就是 blocker」。
3. **收尾命令固定**：`cargo check --workspace` + `cargo clippy --workspace --all-targets -- -D warnings`（CI 口径）+ 各包 test。
4. **cargo 很贵**（`lumen-app` 是超大 crate），中间步骤别反复跑，写完一整块再跑，
   全程控制在 5 次以内。
5. **不要在 `lumen-protocol` 上跑 `cargo fmt`**——该仓库 HEAD 本身不是 rustfmt-clean，
   会重排大量无关既有代码。要格式化只对新建单文件跑 `rustfmt --edition 2021 <file>`。
6. **代码质量判据**（海风哥要求按《代码大全》）：函数 ≤ 200 行（目标 ≤ 60）、
   圈复杂度 ≤ 10、参数 ≤ 7、嵌套 ≤ 4 层；每个新模块要能回答「它隐藏了什么设计决策」
   （答不上来 = 假拆分）；内聚低于「通信内聚」的方案作废。
   **目前 M7 新代码全部达标**：`llm_runner` 264 函数中位 6 行最长 103；
   `remote_ws/llm.rs` 76 函数中位 13 最长 78；`hub.rs` 32 函数中位 8 最长 71；
   超 200 行的 **0 个**。
