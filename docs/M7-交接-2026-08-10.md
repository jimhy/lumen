## 2. 本轮（2026-08-10）做完了什么

### 2.1 两个 HUD bug（与 M7 无关，海风哥 08-09 报的）

细节在 08-09 那份 §9，那一节已改写成结论。这里只留一句根因，因为它是**可复用的教训**：

- **上下文语义反了**，根因不是关键词表写错，是**匹配范围**错——老代码拿**整行**做子串匹配，
  而状态行是多个互不相干的指标拼在一起的一整行，额度那半边的「重置**剩余**」跨段命中了
  上下文的语义判定。修法是把判定单位从「整行」降到「分段」。
- **Claude 的 5 小时 / 本周用量**：数据一直画在同一行上，只是没解析。补了状态行刮取，
  额度是 **JSON 优先、画面兜底**，且画面刮取只对 Claude 开。

★ **一条通用教训**：从终端画面刮取的判定，**判定单位必须是「段」不是「行」**。
误命中的表现是「数值对、语义反」——比彻底读不到更难发现。

### 2.8 片 11：服务端硬化（2026-08-12）

蓝图 §8.2 那张表的 6 条**全部落地**，`lumen-server` 从 41 → 61 passed。

#### ★ 破坏性变更：默认 JWT 密钥现在**拒绝启动**

它是写在源码里的公开字符串，而本服务的 JWT **无 `jti`、无版本号、改密码不失效、TTL 7 天**
——用默认密钥等于任何人都能给任意账户签一张 7 天有效的通行证。一条启动 warn 挡不住这个：
它滚在日志里，而部署脚本没人盯着。

逃生口是 `LUMEN_ALLOW_INSECURE_SECRET=1`，且**只认 `1`**（`=false` / `=0` 都不放行——
「设了就算数」会让一次手滑变成静默的生产事故）。迁移步骤已写进 `server/deploy/README.md`
与 `lumen-server.env.example`，**发布说明必须同版给出**。

#### ★ 背压：队列满时不能用同一个队列通知「你被踢了」

`unbounded_channel` 换成 `channel(256)`。难点在处置：满了要断开那条连接，但
`ToClient::Close` **塞不进去**——通道就是满的那个。所以另开一条 `Arc<Notify>` 旁路，
`ws.rs` 的 `select!` 多一路 `kill.notified()`。

**断开而不是丢帧**：中继上跑的是有序流（终端输出 / 镜像帧 / LLM 增量），悄悄丢一条会让
对端状态永久错位且无从察觉；断开则是客户端已经会处理的情况。

同一条旁路也修好了**驱逐旧连接**：老写法 `let _ = old.tx.send(Close)` 在有界通道上会静默
失败，而队列满的那条连接恰恰是最需要被踢掉的。

#### ★ 节流的 IP 维度会**自动失效**，这是刻意的

反代后面 socket 对端恒为 `127.0.0.1`。拿它当 key 就是**全服务共用一个桶**——
5 次/5 分钟等于整个服务每 5 分钟只允许 5 次登录。那不是节流，是拒绝服务。
所以拿不到真实 IP 时**宁可让这一维不生效**，并在部署文档里让运维显式开
`LUMEN_TRUST_PROXY_HEADER=1`。

另外两条容易写错的：**取 `X-Forwarded-For` 的最后一跳而不是第一个**（前面的部分由客户端
自己发、可以随便伪造，取第一个 = 把 key 的选择权交给攻击者）；**只对失败计数、成功清零**
（否则一个手滑的用户会被自己的正常重试锁在门外）。

★ 登录时**账户不存在也计一次失败**：不计的话这个接口就是一台免费的邮箱枚举器
（`user_not_found` 与 `invalid_credentials` 的差别把「哪些邮箱注册过」全告诉攻击者）。
两个错误码本身的差别是**刻意保留**的（客户端靠它引导注册），所以只能从速率这一侧收口。

#### ★ 设备上限只拦**新建**，认领已存在的行不计数

若认领也计数，超限之后老设备会被一起锁在门外——用户表现是「我什么都没干，突然所有设备
都登不上了」，而真正原因可能只是某台机器换网卡导致 `hw_id` 变化多出一行。

#### `device_pairs` 撤销 API

`GET /api/v1/pairs` + `DELETE /api/v1/pairs/{peer}`（`peer = "*"` 清空本机全部）。
★ 它**解锁了移动端一个悬着的功能**：蓝图 §9.3 的「关生物锁 = 清空本机全部信任对」
此前因为这个 API 不存在，片 6 只能退化成「本地删 token + 提示去 PC 删设备」。

⚠ 撤销只影响**下一次**建会话，**不拆正在进行中的会话**——UI 与文档都要说清楚，
否则用户点了撤销却发现对方还连着，会以为没生效。

#### ★ 变异测试：13 个点，第一轮报「11 全中」是**我的脚本自己假阳性**

判据写成了 `'test result: ok.' in tail_20_行输出`，而测试列表一长，那行就被 `tail -20`
截断了 ⇒ 恒判「被抓住」。**改用退出码之后真相是 10 中 1 漏**：设备配额那条完全没有测试
守着（判定埋在 async + DB 函数里，而那批 DB 测试是 `#[ignore]` 的）。

修法是把判定抽成纯函数 `quota_verdict(count)`（与 `ws.rs` 的 `idle_action` 同一个手法），
补 4 项测试后三种配额变异全部被抓。

⇒ **教训**：08-09 §5.2 记的是「变异测试会假阳性」，这次是它的**新变种**——
假阳性来自**判据本身**而不是变异没生效。判据要用退出码这类不会被截断的信号。

### 2.7 片 9：工具卡片 + diff（2026-08-12）

**验收目标达成**：`Edit` 显示可读 diff；`Read` 卡片折叠态显示「读取 X 第 a–b 行（共 N 行）」

#### ★ 一条边界：入参与结果**不是同一层**，蓝图那句「不许猜字段名」只管后者

蓝图 §7.6 写着「**绝不许照着 `file` 的字段名去猜 `Bash` 会不会有个 `stdout`**」，
§3.3 的「仍未取到」表也确认：`Bash`/`Edit`/`Write` 的 `tool_use_result` 形态**一个都没实测过**。
所以对**结果**只认 `LlmToolResultDetailFile` 这一种结构化形态，其余一律「夹紧字符串 + 折叠 JSON」。

但 diff 的数据源不在结果里，在**入参**（`tool_use.input` 的 `old_string` / `new_string`）——
那是**模型必须按 schema 生成**的公开契约，属于工具定义的一部分，与 CLI 内部的结果形状不是一回事。
所以片 9 会去读它。

「更可靠」不等于「保证存在」：取字段一律走 `_str()`（键不在 / 类型不对 / 空串，三种都返回 null），
任何一步取不到就**退回折叠 JSON**。`MultiEdit` 就是活例子——形态认得出来是 edit，
但它的真实入参是 `{file_path, edits:[...]}`、没有顶层 `old_string`，于是老老实实折叠 JSON。
`tool_card_test.dart` 里有一整组在喂畸形输入：缺字段、错类型、空对象、标量、null。

#### ★ 三条 UI 上的判断

1. **展开状态存在 `MessageList` 的 `Set` 里，不在卡片自己的 `State` 里。**
   气泡流是 `ListView.builder`，滚出屏幕的条目会被销毁——存在卡片里的话，用户展开一张、
   往下滚一屏再滚回来它就自己折叠了。有一条测试真的滚出去再滚回来验这件事。
2. **diff 行首恒带 `+`/`-`，颜色不是唯一判据**（色盲用户与灰度截图）。
3. **不可展开就不画箭头**——与「正在思考…」同一条理由。判据是 `ToolCard.expandable`。

#### ★ LCS 必须有规模上限

两个 2000 行版本就是 400 万格 DP 表。超 `kDiffMaxLines`（400，剥掉公共前后缀之后算）
就**不做 LCS**，画成「改动过大（N 行 → M 行），不在手机上展开」——说出来，
而不是画个空的或转圈到死。

先剥公共前后缀这一步同时让上限极少被触发：真实 `Edit` 的 `old_string`/`new_string`

### 2.6 片 10 + 片 7 收尾：outbox、持久化、离线补齐（2026-08-11）

**验收目标全部达成**：杀进程重开能看到历史；没连上时点发送气泡照样出现、重连自动补发；
进后台会落盘、回前台立刻重连。

#### ★ 这一片最该记住的四条

**① 蓝图 §7.6 那个 `clientMsgId` 在真实协议里根本不存在，得先加。**
蓝图的 outbox 伪代码写着「PC 侧按 `clientMsgId` 幂等去重」，但 `LlmFrame::Send` 只有
`req_id`，PC 侧 `on_send` **没有任何去重**。于是片 10 的第一件事是给协议加两个可选字段
（`Send.client_msg_id` + `TurnStarted.client_msg_id` 原样回带），纯加法、无 `deny_unknown_fields`。

**为什么不能拿 `req_id` 当幂等键**（这条值得单独记）：`req_id` 由**每个控制端各自**从自己的
`RemoteWs::next_req_id()` 分配，而被控端的 `convs` 表是**全端共用**的（一台 PC 上可以同时挂着
桌面镜像控制端与最多两部手机）。两个控制端的 `req_id` 空间完全重叠 ⇒ 拿它去重会把**另一个
控制端的正常消息**误判成重复丢掉，一个不报错、只会让消息凭空消失的 bug。

**② 蓝图 §7.7 的 events 表主键 `(conv_id, seq)` 被真实协议证伪了。**
`TurnEnded` 与前一条 `Delta` **会同号**（片 7 用回放语料实证），而且一条 `Delta` 帧装的是
**多个**块的增量——`seq` 从来就不是「一个条目」的标识，拿它当主键会冲突。
改成 `(conv_id, turn, block_id)`，也就是 `ChatItem.key` 本来的定义。附带收益：落库的 upsert
语义与内存里 `_upsert` 变成同一件事，「快照覆盖一整轮」退化成一条 `DELETE WHERE turn = ?`。
水位线因此移到 `conversations` 表（它本来就是每对话一个值）。

**③ 「实现了但没接线」是一类测试抓不到的缺口。**
`WsClient.onBackground()` / `onForeground()` 从片 5 起就存在、也有测试覆盖，但**没有任何
生产代码调用它们**——「进后台 25 秒宽限、回前台立刻重连」这条 §7.8 的硬指标在真机上
从来没生效过，而所有测试都是绿的。片 10 补了 `ui/lifecycle_bridge.dart` 接上它，
并顺带在进后台时落一次盘。
⇒ **判据**：写完一个「钩子」之后，去 grep 一遍它的调用点。单元测试测不出这种缺口
（被测的那个方法确实工作正常）。

**④ 水位线宁可偏低，不可偏高。**
流式期间 `lastSeq` 每 33 ms 变一次，全写库就是给手机加一个 30 Hz 的磁盘写，所以按秒节流。
这个代价能接受**只是因为方向是安全的**：偏低 ⇒ 重连时多补一段已有内容，归约器的幂等规则
正好吸收；偏高 ⇒ 那一段永远补不回来，两端都没有任何迹象。
⇒ 所以只在**内容真的落库之后**才推水位线，绝不能反过来。

#### 变异测试：19 个变异点，2 个没被抓住

按 08-09 §7 的纪律，收工前逐个打断关键通路。Dart 侧 13 个、Rust 侧 6 个，**两个漏网**：

   复用了这条拒因（新增拒因会打掉老客户端唯一的回执）。
3. **十个 `DenyReason` 各有文案，两个不能笼统**：
   - `AlreadyControlled` 在隐藏桶里是「该电脑的手机会话已达上限（**2**）」，
     **必须给具体数字**——只说「已被占用」会让用户去找一个并不存在的占用者；
   - `TargetPairing` 是「该电脑正在与另一台设备配对，请稍候」，**不是**「已被占用」
     （这条文案 §6 从 08-09 起就挂着待改，片 6 一起清掉）。
4. **生物锁与免码的强制绑定**（§9.3）：关掉生物锁 = 调 `DELETE /api/v1/pairs/*` 清空本机
   全部信任对。⚠ **那个撤销 API 现在还不存在**（片 11 才补），所以片 6 落地时要么先只做
   「关生物锁 = 本地删 token + 提示用户去 PC 上删设备」，要么把片 11 的这一条提前。
   **不要静默地只关生物锁**——那正是「把一个已知会塌陷的组合交给用户」。

### 4.4 二维码那条链路（片 6 的另一半，在 PC 侧）

`crates/lumen-protocol/src/pairing_qr.rs` 与 `crates/lumen-app/src/remote_pairing_qr.rs`
**都还不存在**，要新建。扫码要携带 origin，手机端**必须比对**：扫到的 origin 与本机已登录的
不一致时显示安全警告而不是静默切换服务器——切过去就是把凭据发给另一台服务器。

### 4.5 写 Dart 协议类型时必须遵守的四条（已经被测试钉死）

1. `Option` + `skip_serializing_if` 的字段，`toJson` 里必须让键**整个消失**，
   用 `writeOpt()`；而带 `default` 但**不带** skip 的字段相反，输出里一定要出现。
   两者混淆是手写模型最常见的漂移。
2. 整数字段**只认 `int`，不接受 `double`**。Dart 的 `num` 相等跨 `int`/`double`
   （`240262 == 240262.0` 为真），所以一处存成 `double` 几乎不会被往返断言发现。
3. **未知内容降级但不回显**，不设 `extra` map。任何「先收下来、以后再说」的容器
   都是白名单转发的后门。
4. **（片 5 新增）分清哪一层有兜底**：内层 `LlmFrame` 与它嵌套的那些 tagged 枚举有
   `Unknown` 降级；**外层 `RemoteC2S` / `RemoteS2C` 与那四个 C 型枚举没有**——它们是外部标签
   枚举，未知变体/未知取值都是整条报废，两端都必须**抛**而不是宽容。把这一层「顺手加个兜底」
   反而与 Rust 不一致，`control_plane_golden_test.dart` 有断言守着。

### 5.7 ★★ 两个会话同时编译 → rustc 进程内存损坏（2026-08-11，**已定位**）

**根因：两个 Claude Code 会话并发对同一个 `target/` 跑 cargo。**另一个会话结束后，
`cargo build -p lumen-app` 立刻恢复（16.34s 通过），改动一行没动。

这条值得记下来，因为**它伪装成了代码问题**，害我排查了三轮：

| 观察到的现象 | 当时的（错误）推论 |
|---|---|
| 加 `qrcodegen` 就崩，撤掉就好 | 「是这个 crate 的问题」 |
| 换成 `qrcode` 还是崩 | 「是 lumen-app 依赖数量到临界了」 |
| 撤掉全部新依赖仍然崩 | 「是 rustc 自身 bug / 硬件 / 杀软」 |

三次崩溃给出**三种不同错误码**（`STATUS_ACCESS_VIOLATION` 0xc0000005、
`STATUS_HEAP_CORRUPTION` 0xc0000374、`STATUS_STACK_BUFFER_OVERRUN` 0xc0000409），
而 `cargo check` **每次都干净通过**——现在回头看，「三种内存错误 + check 通过 +
撤销改动也不稳定复现」这个组合本身就该指向**进程外的干扰**，而不是某一处代码。

⇒ **判据**：`cargo build` 崩在 codegen 且错误码在几次之间变来变去时，
**先确认没有第二个会话/终端在跑 cargo**，再去看代码。cargo 的文件锁挡得住同一个
crate 被编两次，但挡不住两个 rustc 进程同时读写 `target/debug/incremental` 与 PDB。

> 顺带一条协作纪律：多个会话同时开工时，**别让两边都跑 cargo**。Flutter 侧
> （`mobile/`）与 `lumen-protocol` 这类小 crate 不受影响，可以并行。

现象：给 `crates/lumen-app/Cargo.toml` 加一个新依赖后，`cargo build -p lumen-app` 在
codegen 阶段崩溃：

```
error: could not compile `lumen-app` (bin "lumen")
process didn't exit successfully: rustc ... (exit code: 0xc0000005, STATUS_ACCESS_VIOLATION)
                                            (或 0xc0000374, STATUS_HEAP_CORRUPTION)
```

**已做的排除**（结论：不是代码问题，也不是某个特定 crate 的问题）：

| 试了什么 | 结果 |
|---|---|
| `cargo check -p lumen-app --all-targets` | ✅ **通过**（只有未接线的 dead_code warning）⇒ 类型层面没问题，崩在 codegen |
| 换库：`qrcodegen 1.8` → `qrcode 0.14` | ❌ 一样崩 ⇒ 不是某个 crate 的锅 |
| 清 `target/debug/incremental` | ❌ 一样崩 ⇒ 不是增量缓存损坏 |
| 撤掉那一个依赖 | ✅ **立刻恢复**（5.87s 编译通过） |
| 内存 | 63.7 GB 总 / 36.8 GB 可用 ⇒ **不是 OOM** |
| `RUSTFLAGS="-C debuginfo=1"` 全量重编 | ❌ 连 `wgpu-hal`、`lumen-ssh` 这些**与改动无关**的 crate 也崩 |
| **撤掉全部新依赖后再编** | ❌ 仍然崩（第三种错误码）⇒ 不是「加依赖」引起的 |
| `cargo check -p lumen-app` （撤掉依赖后） | ✅ 2.39s 通过 ⇒ 代码本身是好的，只有 codegen 崩 |
| **另一个会话结束后再编** | ✅ **16.34s 通过** ⇒ 根因就是并发编译 |

最后一行值得单独记：全量重编时无关 crate 也崩，说明这台机器上的 rustc 在**并行编译大 crate**
时本身就在稳定性边缘，而 `lumen-app` 加一个依赖只是把它推过了线。

**没有验证过的候选解法**（都影响全项目，需要海风哥拍板）：

1. **升级 rust toolchain**（当前 stable-x86_64-pc-windows-msvc）——最可能是上游已修的 bug；
2. `[profile.dev] debug = 1`——减小调试信息规模，代价是断点调试体验；
3. 降低并行度（`cargo build -j 2`）或换 linker（lld）；
4. 把杀软对 `target/` 的实时扫描排除掉——Windows 上这类「随机 ACCESS_VIOLATION」的常见来源。

**在它解决之前**：`crates/lumen-app/src/remote_pairing_qr.rs` 已经写好（含 4 条测试）但
**没有 `mod` 声明、不参与编译**。解决之后只需要两步：`main.rs` 加一行 `mod remote_pairing_qr;`、
`Cargo.toml` 加一行依赖。**先跑一次 `cargo build -p lumen-app` 确认基线是绿的再动手**，
否则会把工具链问题误判成自己写错了。

> 附带的产品选项：扫码在 K13 里是「P0 做」，但它只是 9 位数字码的**另一种呈现**——
> 数字码那条路径本来就在。真要绕开这个阻塞，可以先发「手输 9 位码」的版本，
> 扫码等工具链修好再补。**这是海风哥的决定，不是可以顺手替他做的。**

### 5.5 ★ 一次「只读」的 `flutter analyze` 悄悄改掉了 146 行 `pubspec.lock`

本机把 `PUB_HOSTED_URL=https://pub.flutter-io.cn` 设成了**全局**环境变量，而
`flutter analyze` / `flutter test` 都会**隐式**跑一次 pub get。pub 把 hosted URL 当作依赖
身份的一部分：环境里的 URL 与 lock 里的对不上时，它会**忽略 lock 重新解析整个依赖图**，
顺手把依赖升到最新兼容版本（实测 `test` 1.26.3 → 1.30.0），再把镜像 URL 写回 lock 的
每一条 `url`。

后果是 CI 的 `flutter pub get --enforce-lockfile` 第一步就红，而**本地看不出来**：
diff 里只是一堆 URL 和版本号，很容易当成「谁顺手升了个依赖」。

老写法只在 `--pub` 分支归一化 lock，`analyze` / `test` 这两条**更常跑**的路径完全不设防。
片 5 已在 `tool/test.sh` 与 `tool/test.ps1` 的非 `--pub` 分支把 `PUB_HOSTED_URL` 显式钉回
`https://pub.dev`（不是摘掉——摘掉会退回默认值，效果一样但看不出意图）。

⇒ **判据**：跑完任何 flutter 命令后，`git status mobile/pubspec.lock` 应当是干净的。
不干净就是又踩了这条。

### 5.6 ★ 蓝图 §7.5 的「已配对免码直连」对隐藏会话**不成立**（以服务端代码为准）

蓝图写「已配对设备跳过配对码直达 `LinkActive`（`hub.rs:387-390` 的 `if paired`）」——
那对**镜像**会话成立，对**隐藏**会话不成立。片 4b 落地时做了止血，两处一起看才完整：

- `ws.rs` 的 `OpenHidden` 臂**恒传 `paired = false`**；
- `hub.rs::submit_pairing` 在 `ControlKind::Hidden` 分支**恒返回 `None`**（⇒ 不写 `device_pairs`）。

理由是 `device_pairs` 只有 `(user_id, dev_lo, dev_hi)`、**没有会话种类列**，两类会话共用一行
信任会双向越权：手机为「跟 LLM 说话」念的那次码会**同时**授予它日后免码建**镜像**会话的能力
（全屏 + 远程输入）；反向则让一台早年为镜像配过对的桌面端免码开一条**隐藏**会话——而隐藏会话
在被控端**没有横幅、没有指示器、没有结束入口**，等于把有 UI 的通道换成同等权力、零指示的通道。

⇒ **手机端每次都要念码**，UI 不要做「记住这台电脑」。
⇒ 片 5 的 `LinkController` 仍保留 `LinkRequesting → LinkActive` 的直接跃迁（服务端那条
`if paired` 分支还在，将来加了 kind 列就会走活），但**不能假设它会发生**。

同源的第二条：**断线即会话消失**。服务端 `disconnect` 立刻 `teardown_hidden_for_device`，
没有重连续挂——蓝图里那个 `LinkReattaching` 状态因此**没有实现**（留一个永远到不了的状态，
只会让后人以为有重连续挂机制）。
